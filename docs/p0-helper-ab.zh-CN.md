# 启用新增 helpers 的旧版／新版对照

**这次实际启用了 helpers，但未观察到漏检或外部纠正减少。PR #20 保持 Draft，不合并。**
本次只增加报告和原始证据，没有修改 helper 实现、技能入口、测试或 CI。

## 对照范围与公平基线

沿用 [OpenTitan OTBN WFI 历史修复](https://github.com/lowRISC/opentitan/pull/31507)
的固定源码：原始 `2c36b23a`、修复后 `de113e39`，每边 17 份文件、3 份实际修改。
这是修复交接和相关遗漏审查；已知根因／补丁提供给两边，不重新把它当盲根因分析。

| 项目 | 旧版 | 新版 |
| --- | --- | --- |
| kit 固定版本 | `4f897552` | `dac1c5ee` |
| 通用能力 | Python、rg、文件读取及工作区脚本 | 相同 |
| 修复检查 | 旧指导／旧运行时，自行审阅或编写检查脚本 | 实际 `dv fix-snapshot`、`dv fix-report` |
| 相关遗漏搜索 | 通用查询和语义审阅 | 实际 `dv variant-search`，再审阅候选和源码 |

没有要求旧版徒手逐项比 SHA；旧版确实自行编写了自动审计脚本。
新版须自行创建 variant plan、执行 helpers、保存输出并处置候选，不能只引用工具名称。
两边共用预制的 profile、修复计划和记录输入，**未测真实项目 collector 的接入／维护成本**。

一次完整交接包含下面三套证据和一次相关源码搜索。两轮成对重复，共 4 个原生模型会话，
交替先后顺序；请求相同 `gpt-6.1-sol`、medium，每次 300 秒、20 次 shell 调用。
插件、联网检索、自动 skill 发现和多 agent 关闭。只有隔离的 `project/work/` 可写。
协议、输入／运行时摘要和 oracle 在模型运行前封存。
四次均完成，没有超时、替换重跑或源输入修改；实际模型后端构建号未独立核实。

## 真实材料与受控记录

公开修复报告缺少逐次 commands、seeds、工具版本和完整日志。
本次抓取的 [OTBN latest report](https://reports.opentitan.org/hw/ip/otbn/dv/uvm/latest/report.html)
展示 2025 年结果，未用来证明本次 2026 修复。**本机未执行 VCS／Xcelium。**

| 输入 | 性质 | 预先规定的判断 |
| --- | --- | --- |
| q5 | 公开报告和源码的实际证据缺口；五项检查均无逐次记录 | 缺十个 base/patched 记录，variant review 待做 |
| k8 | 明确标记为受控 collector fixture | 分别发现失败签名错误、patched baseline 摘要不符、证据文件摘要变化 |
| m2 | 自洽但明确非真实仿真的受控记录 | 可满足机械合同；不能支持工程验收 |

k8/m2 不是实际 EDA 运行记录。没有捏造具体 simulator 版本、命令或 seed：它们保持
`UNREPORTED`／`null`，并明确注明未知。故障注入有明显字段／文本线索，是较容易的
合同检查；不能把检出率推广成真实项目中隐蔽问题的检出率。

源码 oracle 预先固定两处已由上游审阅支持的相关 coverage 遗漏：
`get_operational_state` 缺少 PAUSED 分类，及 `CmdResume` 被计入 BogusCmd。
它们是同一 WFI 支持家族的不同遗漏，不是独立复现的两个 DUT bug。
旧／新版本位置和同一原因的多个调用点只计一次；修复中的正常清空／有界检查等作为反例。

## 漏检、误采信与介入

评分由主会话 AI 对照封存 oracle、原答案及原始记录完成，不是独立工程师盲评。

| 两轮累计，限定本输入集合 | 旧版 | 新版 |
| --- | ---: | ---: |
| 三处受控记录错误检出 | 6/6 | 6/6 |
| 两处已知源码遗漏检出 | 4/4 | 4/4 |
| 把模拟／报告记录误当工程验收证据 | 0 | 0 |
| 已知合法反例被误报为 bug | 0 | 0 |
| 触发的模拟外部纠正提示／轮次 | 0／0 | 0／0 |
| 真实工程师分钟数 | 未测 | 未测 |

分母来自一个案例的重复，不是六个真实历史错误或四个独立项目。
旧版将 k8 称为 `invalid`，新版工具返回 `gaps`；两边都指出三处具体问题，标签差异不算漏检。
两边均区分 m2 的机械一致性与工程证据有效性，没有直接采信 `ready_for_review`。

按预案，漏掉必要项时会增加一次固定的纠正会话，并保留首轮结果；本次没有触发，
因此没有再启动模型。纠正提示本来也由主会话 AI 模拟，**不是实际工程师计时**。
基线已经没有这些预设漏项，样本存在明显上限，无法据此证明 helpers 普遍无用或普遍有效。

所有额外源码发现都保留：包括 CTRL coverage、暂停时的 memory/checksum 和 alert/timing
候选。这些超出封存 oracle，尚无独立专家／执行证据完成处置；既不计作已证明的新收益，
也不直接判为误报。不同的候选数量／分类不能换算成人工工作减少。

## 实际 helper 轨迹揭示的边界

新版两个会话共执行 **15 次被测核心命令调用**：4 次 snapshot、6 次 fix-report、5 次 variant-search。
离线恢复固定运行时后，全部 JSON 输出和退出码与原始调用一致。
help／template 查询另保留在原生轨迹中，其成本已包含在会话统计内，不计入这 15 次。

`fix-report` 两轮都自动指出 k8 的三处合同问题；旧版脚本也全部找到。
m2 两次均返回 `ready_for_review`、`signoff=false`，而支持文件仍明确非真实执行。
这符合它依赖 collector 声明的边界，证明的是机械校验能力，不能认证 collector 的真实性。

两次初始 variant 搜索都耗尽 300 个候选预算，均保留不完整结果，并由模型自行调整计划：

| 轮次 | 实际搜索调用 | 完整结果中的候选数 | 额外操作 |
| --- | ---: | --- | --- |
| 第一轮 | 2 | 109 | 一次预算耗尽后的收窄 |
| 第二轮 | 3 | 241、264 | 一次收窄及一次后续扩展 |

第一轮完整 literal 列表没有命中 CmdResume 缺失的 covergroup；模型额外审阅源码才找到。
第二轮后续计划加入 `get_operational_state`、`BogusCmd` 等词，最终能定位已审阅的问题区域；
不能把最终命中自动记成 helper 独立发现语义遗漏。候选工具没有自动代替语义审阅。
第一轮新版还遇到一次错误 shell glob，自行纠正；没有 helper 无效调用或外部人工接管。

模型会话总耗时旧／新为 456.75／455.63 秒，基本相同；shell 工具调用为 27／29。
这些都不是工程师工时。token 原始用量保留在 JSON 中，本轮不把它当作收益验收指标。

## 结论与复核

已证明 helpers 能实际运行、复查输入摘要、返回可回放的合同缺口／候选结果。
**相对同样允许脚本化的旧流程，本次未减少已知漏检、误采信或模拟外部纠正。**
两边仍需真实运行记录、语义处置和工程验收；没有实际人工成本改善证据。
不据此合并，也不继续扩展框架。
